# Vision

LucidPlan is a project management system written end to end in Scheme: Guile, Artanis, SQLite, Olive CSS and some vanilla JavaScript, with the views in Hygguile and the authorisation in Bewaking. It has a backlog, a kanban board, sprints with a burndown, milestones, time entries, threaded discussion, attachments, an audit trail, planning poker and a REST API. This document is about the two things that shape everything else in a tool like this — who is allowed to do what, and which record is the truth — and about the part of the project that is ahead of its own tests.

## Where lucidplan is today

The code is organised as repository, domain and controller: `lib/lucidplan/domain/` holds the records, `lib/lucidplan/sqlite/` the persistence, `app/controllers/` the routes and `app/views/` the Hygguile pages. `tickets.scm` alone is 2,499 lines and `poker.scm` 899, with `domain.scm` and `html.scm` as the two large shared libraries. Schema migrations are Mutastructura's and one task applies them. The instance's identity — name, tagline, keywords, logo, mail sender, password policy, attachment ceilings, locales, ticket statuses, landing-page copy — lives in an `env.scm` module that is per deployment and deliberately not committed.

The feature list is far past a kanban toy. Tickets carry a type (`Task`, `Bug`, `Story`, `Spike`, `Time Box`), a configurable status ladder, Org-mode descriptions rendered to HTML, story points and t-shirt sizes, an assignee, a due date and a milestone. A ticket has a threaded discussion where a reply is drawn under what it answers, attachments that are downloaded through the application rather than by path, and a numbered version history where a restored version becomes a new version rather than rewriting an old one. Time entries parse `1.5h`, `90m`, `1h30m`, `1h 30m` and `1:30` as the same ninety minutes. Sprints draw a burndown from the audit trail the tickets already leave, so the chart cannot disagree with the tickets it is about. Planning poker gives a whole table of guests a way to estimate something without any of them having an account.

Three facts about the design matter more than the feature list, and they are the subject of this document.

**Permissions are instance-wide flags on a user record.** Seven `lucidplan:*` permissions exist — ticket and project create and delete, user create and delete, and `modify-permissions` — and a token carries a list of them. There is no membership model at all: `notifications.scm` says so in its own commentary, that "who takes part" is not a membership list, because LucidPlan keeps none, so it derives participants from who has been assigned a ticket. Every project in a workspace is visible to every authenticated user, and there is no notion of a private project.

That is a deliberate simplification and it is the right one for a team that trusts itself, which is the team this tool is aimed at. It is also the first thing that stops a deployment: the moment a workspace holds a project one person must not see — a hiring round, a client's work, a security issue — the model runs out. The permissions being a native Lisp list means the ACL is programmable; it does not mean it is scoped.

**The audit trail already underlies more than it looks.** Every write records who, when, the field, the value before and the value after, and the burndown is computed from that record rather than from a counter. This is the most valuable decision in the codebase and the one with the most unclaimed consequences.

**The API is a keyhole.** `/api/v1` has three endpoints — login, the project list, a project's tickets — and each read passes an empty permission list, so a token is required and no specific capability is asserted. The ACL that the pages enforce in detail is not yet expressed in the API.

The unreleased section of `CHANGELOG.org` is larger than the last release: swimlanes (`?lanes=epic`), labels, saved filters, bulk changes, and a set of upload fixes that are worth reading as a lesson about form handling in Artanis. Those are in the tree and not in a tag.

The upload fixes are the most instructive entry in the whole changelog, because they are the kind of bug a self-hosted tool lives or dies by. A request whose body the multipart reader could not make sense of raised where it stood; a route that answered with nothing at all left the browser waiting for a response that never came; and the framework's own `upload.size` ceiling sat at exactly the application's limit, so the multipart framing around a five-megabyte file was enough to make the framework refuse the request before reading it. The fixes are all the same shape — answer with a redirect, carry the reason in the query string, say it beside the control that was used — which is the right shape, and the reason that entry is worth keeping.

The test surface is the honest weak point: six unit specs — ticket triage, estimates, threads, time entries, burndown and planning poker — plus a benchmark, against some twelve thousand lines of controllers and library code. The specs are good and they are about the right things, which is the pure logic; what is untested is the layer where a project-management tool actually spends its risk, which is writes and access control.

The rest of the process is in better shape than that number suggests. Every push to `trunk` runs the suite on Byggsteg before anything is deployed, asked for by a GitHub Actions workflow that calls a reusable job rather than carrying the steps in this repository; the job is `maak-test`, `pull-and-restart` and `maak-deploy`, and the build goes green or red according to what the deployment said it did. That is a stronger gate than most projects of this size have, and it makes the missing tests more visible rather than less.

## The vision

1. **Membership, and therefore private projects.** A project is a place with people in it, and today there is no way to say who. In a few years a project has members, a role per member, and the permission checks consult the project as well as the user — so a contractor sees one project and not the other eleven, and the notification audience stops being an inference from assignment history. This is the largest missing concept in the product, and it is the one every serious deployment asks for first.
2. **One permission model, enforced in both interfaces.** The pages ask Bewaking for `lucidplan:ticket-create` before a write; the API currently checks only that the token is valid. In a few years a single predicate decides every route, the API asserts the same permissions the pages do, and a test enumerates the routes against a user with none, some and all of them. An access-control list that is enforced in one of two interfaces is not an access-control list.
3. **The event log is the truth, and every report is a view of it.** The burndown already proves the pattern: it is computed from the audit trail, so it cannot drift. Velocity, cumulative flow, time reports and a milestone's progress should all be derived from the same events and the same time entries, with nothing stored twice. A project management tool that keeps two answers to one question will eventually show both.
4. **Every question has an address.** The backlog's state already lives in the query string, and a saved filter is a name for one — which is a good design and an incomplete one, because a saved filter is per user and invisible to anyone else, and a lane or a sprint scope is not saveable at all. In a few years every narrowing of every view is a URL, a saved view is a shared object the project owns, and a link in a chat is the whole answer.
5. **The suite covers the writes.** Twelve thousand lines of controllers against six pure-logic specs is a ratio that will not survive the feature set. In a few years the routes that write — a ticket move, a bulk change, a version restore, an attachment, a permission edit — have tests that drive them as a user would, and the router is exercised with a token that should be refused.

Statements 1 and 2 are the same subject seen twice: who is allowed to do what, and whether every door asks. Statements 3 and 4 are the other pair: what is the record, and how is it addressed. Statement 5 is the one that makes the rest safe to change, and it is ranked last only because it is the least interesting to write and the most valuable to have.

The ordering in the code tells the same story. Permissions were in place before there were projects to scope them to, which is why they are instance-wide; the audit trail was in place before anything needed to be derived from it, which is why the burndown was cheap to add. Deciding these things in the right order is the whole difference between a project-management tool that grows and one that has to be rewritten.

## Features that are in scope and not built yet

Each of these is a seam the code has already cut.

- **Project membership.** `notifications.scm` derives its audience because there is no membership list, and the ACL has no per-project dimension. *The hard part* is that adding membership changes the meaning of every existing permission: a deployment that works today must keep working, and the migration has to decide what an existing instance's memberships are without a human typing them in.
- **Writes in the API.** `app/api/v1.scm` is 94 lines of reads and a login. *The hard part* is that an API write is not a controller call with JSON in place of a form — it needs its own validation, its own error shape, and a decision about partial updates that the pages never had to make.
- **Saved views that belong to the project.** Saved filters store the query string as text and validate it against the shape the page's own links have, which is exactly right. *The hard part* is sharing: a saved filter is currently a personal name for a personal narrowing, and making it a project object raises the question every shared view raises — who may change it, and what happens to a link when they do.
- **Sprint velocity and the reports that follow.** The burndown exists and is derived. *The hard part* is that velocity is a claim about the future made from the past, and a project-management tool owes its users honesty about what it is extrapolating rather than a confident line.
- **A per-person notification setting.** There is one notification: a new ticket, sent to everyone the project has put to work. *The hard part* is that a useful notification needs a preference per person and per event, and the mail service is a single template call away — so the shape of the setting is decided by the mail layer's shape, not by what a user would want.
- **The i18n catalogs.** Four languages ship — English, Dutch, Spanish, Japanese — and new strings are collected by three `maak` tasks in sequence. *The hard part* is that forgetting the middle task is silent, exactly like forgetting to regenerate a generated asset, and the fix is a test rather than a reminder.
- **The theme.** `pub/` carries the three web families, the icon face and the stylesheets, served by the instance, refreshed by `maak fetch-assets`. *The hard part* is that a self-hoster may want their own colours, and the stylesheet is committed rather than generated, so an override needs somewhere to live.
- **A second database.** SQLite is the right default and nothing above the repository layer knows it — `lib/lucidplan/sqlite/` is a set of implementations behind domain records. *The hard part* is that the one thing SQLite buys, a file you can copy, is also the thing a larger deployment outgrows, and the cost of supporting both is a test matrix nobody has time for.
- **Search that covers descriptions.** There is a global search in the interface. *The hard part* is that descriptions are Org text rendered to HTML, so a search over them has to decide whether it searches the source, the rendered text or both, and those give different answers.
- **The status ladder's edges.** `(value label icon glyph bucket)` decides what a ticket moves through, and the bucket is what turns a status into "done" for the summary and the burndown. *The hard part* is that renaming a status is configuration while changing its bucket changes history's meaning, and the two are edited in the same list.
- **The 404 inside a project.** A ticket number is a project's own sequence, and a URL naming a ticket that has moved — which LucidPlan allows — has to resolve or explain. *The hard part* is that moving a ticket keeps its history and its discussion, so the old address is a real thing to redirect rather than a missing row.

## New features that would be worth having

- **A project's own settings page.** Beyond statuses, which are already per-project: which lanes, which label vocabulary, which sprints are open, who is in it. *Why it is worth having:* the instance-level `env.scm` is the right place for what the installation is, and the wrong place for what a project is, and the boundary is currently drawn by whoever wrote the last controller.
- **A CLI.** The API is the hard part; once writes exist, a `lucidplan` command that opens a ticket from a commit message or lists a sprint is a few hundred lines and a genuinely different way into the same data. *Why it is worth having:* it is the feature that makes the tool usable by people who do not want a browser tab for it.
- **A roadmap view over milestones and sprints.** The data is all there — milestones with dates and progress, sprints with start, end and a goal — and the only view is a page per thing. *Why it is worth having:* it is what "multi-project" means to anybody above a certain size, and it needs no new model. *(Speculative in effort: a timeline is a real piece of interface.)*
- **Real-time board updates.** Two people on one board see each other's changes only when they reload. *Why it is speculative:* a websocket in Artanis is a different architecture from a request that renders a page, and the honest cheaper version is a poll with the board's own version number — which the audit trail can already provide.
- **A work-in-progress limit per column.** The status ladder is configuration and the board already knows how many tickets are in each column. A limit with a visible warning is the entire value of kanban in one rule. *Why it is worth having:* it is a few lines and a colour, and it is the feature that makes the board teach the method.
- **A daily digest.** The notification layer knows what changed; a mail per project per day rather than per event is what people actually read. *(Speculative in design: a digest is a mail template and a scheduler, and the scheduler is the part this deployment model does not have.)*
- **A public board.** Poker already proves that LucidPlan can hand something to a person with no account. A read-only board behind a share token would let a project show its status to the world. *(Speculative, and it is a security decision before it is a feature.)*
- **A spreadsheet import.** Columns in, tickets out, with a report of what could not be mapped — the reverse of the export nobody has written either. *Why it is worth having:* it is the migration path from the real incumbent, and it would force the project to say out loud what a ticket is.
- **A keyboard map for the board.** With `me.scm` and the accessibility section already caring about focus and keys, and Hygguile shipping a command palette, the missing piece is the set of verbs a keyboard user needs: move to the next column, open a ticket, assign myself. *(Speculative in scope: it is a genuine design exercise in a view layer that currently relies on the browser's own drag and drop.)*

## Contributions that would move the needle

1. **A route test with a token that should be refused.** The suite already runs pure logic; this is the first test that drives an HTTP route as a user with no permission and asserts the refusal. *Why it is a good task:* it is a day's work, it names the pattern for every subsequent test, and it converts statement 2 from an intention into a place to put code.
2. **Membership, as a design first.** Write the migration and the predicate, accept the API and the pages in a second patch. *Why it is a good task:* it is the one concept whose absence is visible to every deployment, and the interesting part — what an existing instance becomes — is a design problem the project should solve in public.
3. **A tooltip that explains a status.** The status ladder is configurable, which means it is not self-explanatory: `(value label icon glyph bucket)` is a tuple a new user has to learn. *Why it is a good task:* it is small, it improves the first hour, and it exercises the view layer that Hygguile makes pleasant.
4. **The i18n check in `maak test`.** Fail when a string in the sources is missing from the catalogs. *Why it is a good task:* it is an hour and it protects four languages from silent decay.
5. **A time report.** Time entries already exist per ticket with a day and a duration; a per-project, per-person, per-week total is a query and a page. *Why it is a good task:* it is the feature contractors ask for, it needs no new model, and it is the first view to be derived from the events rather than stored.
6. **Poker's hand-off, made obvious.** Writing the agreed estimate onto the ticket is the one part of a poker round that needs an account, and the transition is where a table gets confused. *Why it is a good task:* it is a piece of interface in the most unusual feature the project has, and the unusual features are the ones that need the polish.

The ranking is value per hour, and the first item is deliberately the least glamorous: a refusal test is what turns the ACL from a claim into a mechanism. Item 2 is the biggest product decision on the list and is ranked second because it should be designed before it is built, in the open, with the migration visible. Items 3 to 6 are all small and all about the experience of the first week, which is where a self-hosted tool is won or lost.

What is not on the list: a Gantt chart, a wiki, a time-tracking timer, integrations. Every one of them is a real feature in a real competitor and every one of them moves the deployment shape away from one process and one file, which is the property that makes this thing different.

## Compared to related projects

| Project | What it is | Where lucidplan differs |
|---|---|---|
| Jira | Atlassian's issue tracker, the one everybody has used and many have fled | The project's own origin story. Jira wins on integrations, workflow engines and enterprise administration; LucidPlan wins on being a single Scheme codebase and a SQLite file you can read, and on a board that loads in the time it takes to blink. |
| Trello | Card-and-list boards with almost no model behind them | Trello is a whiteboard: no statuses, no backlog ordering, no estimates, no audit trail. LucidPlan is a board plus a backlog plus the arithmetic around them, and it is self-hostable by one person. |
| Linear | A fast, opinionated issue tracker with a strong command interface and keyboard-first design | The closest thing to a modern benchmark, and closed source. Linear's speed and its opinionated workflow are what LucidPlan should study; LucidPlan's answer to customisation is Lisp rather than a settings tree, which is the same bet the whole ecosystem makes. |
| OpenProject | A large free-software project management suite with Gantt, budgets, wikis and meetings | Far broader and far heavier, and it needs a database server and a Rails deployment. LucidPlan is deliberately smaller: one Guile process, one SQLite file, and no feature that needs a background worker. |
| Taiga | Free-software agile project management with Scrum and Kanban, in Python | The closest free-software comparison in feature terms: backlog, sprints, burndown, wiki, issues. Taiga is a Django application with a service architecture; LucidPlan is one process, and its extension language is the language it is written in. |
| Plane | An open-source Jira alternative in Django and React, with cycles and modules | The modern successor in the free-software space, and the one a self-hoster is most likely to compare against. It has issues and cycles; it does not have planning poker, a Scheme extension point or a burndown computed from an audit trail. |
| Kanboard | A small, fast PHP kanban tool with a plugin system | The nearest neighbour in spirit: deliberately simple, self-hosted, one database. Kanboard is a kanban board and stops there; LucidPlan's backlog, sprints, milestones, time entries and poker are the answer to "and then what". |
| GitHub Projects | Boards over GitHub issues, with custom fields and views | It wins on being where the code already is, and it has no notion of time, of estimates in two currencies, or of a sprint with a goal. It is the tool LucidPlan is most often *instead of*, which is worth knowing. |
| A shared spreadsheet | The row-and-status-column sheet a small team uses before it adopts anything | Wins on flexibility, familiarity and export, and has no workflow, no unrewritable history and no burndown. It is the real incumbent for the deployments LucidPlan is aimed at, and migrating from one is the most useful documentation the project could write. |

What the others do that lucidplan could still add: Linear's keyboard-first interaction and its command palette are the single biggest usability gap, and the Hygguile component library already ships a command palette. GitHub Projects' saved views are shared, addressable and cheap — the model statement 4 wants. Kanboard's plugin system is the mature version of "extend it with Lisp", and OpenProject's roadmap view is the one reporting feature whose absence is felt at every standup.

There is also a comparison worth making with the tool LucidPlan is most likely to replace in practice: a shared spreadsheet. A sheet of rows with a status column is what a two-person team uses before they adopt anything, and it wins on flexibility, on familiarity and on export. What it cannot do is enforce a workflow, keep a history that a person cannot quietly edit, or compute a burndown — which are precisely the three things this project is for, and the reason its migration story from a spreadsheet would be a genuinely useful thing to write down.

Where lucidplan is ahead and should stay ahead: the burndown is computed from the audit trail, so the chart and the tickets cannot disagree — most tools of this size store a snapshot and drift. Planning poker admits guests without accounts, which no comparable tool does. The permission list is a native Lisp list, so an ACL is data a script can write. And the whole thing is one process and one file, which is why an instance is something a person can run rather than something a person must administer.

## In the long run

The long bet is that a project-management tool is a database with a point of view, and that the point of view is worth owning. LucidPlan's is written down: a backlog ordered by priority, a board with a configurable ladder, estimates in two currencies, a sprint with a goal, and a history that cannot be rewritten. Everything the project adds should be a view of that, and the reason the audit trail matters so much is that it is the only place where the point of view is enforced rather than merely displayed.

The second bet is on Lisp as the extension language. A self-hoster who wants a different workflow should be able to change the workflow, not file a feature request, and the ACL being a list of symbols is the small proof of the idea. The large proof would be a project whose settings are code — which is why the per-project settings page in the list above is written as "settings", not "a form".

That bet has a prerequisite worth naming: a project whose behaviour is code needs a place to put code that is not a fork. `env.scm` is per deployment and uncommitted, which is the right shape for secrets and identity and the wrong shape for a project's workflow, because it is not versioned, not shareable and not something a project owner can edit. Where a per-project snippet of Scheme would live — and whether it should exist at all, given that a database row containing a closure is a deployment hazard — is the design question beneath the extension-language claim.

The third bet is about the deployment shape. One Guile process, one SQLite file, a `manifest.scm` and an `env.scm` that is not committed. That shape is what makes the tool available to a two-person team, and every feature that requires a worker, a cache or a second service trades it away. The poker table, which runs without accounts and without a session store, is the model: the constraint produced a better feature than the unrestricted version would have.

What would falsify these bets: if the teams this is aimed at turn out to want integrations more than they want ownership, the deployment shape becomes a liability rather than an advantage, and the honest response is a webhook out rather than a plug-in in. If Guile's web stack stalls, the cost of the language bet rises every year regardless of how good the code is. And if AI-assisted tooling makes a proprietary tracker's onboarding cheap enough that nobody self-hosts, then the argument for this project is the same one it always was — that the data is yours and the file is readable — and it will be made to a smaller audience.

## How to read this document

The in-scope list names things the code has already half-committed to — several of them visible in a module commentary that explains what the code does not have. The rest are proposals, and the speculative ones are marked. `CHANGELOG.org` is the record, and its unreleased section is not a promise about dates.

The one thing worth taking from this document even if nothing else lands: the two questions that decide whether LucidPlan scales past a single team are who is allowed in a project, and whether every route enforces the same answer. They are cheap to design now and expensive to add once a deployment has data.

*This document describes intent, not commitments; the controllers, the schema migrations and the suite remain the only account of what LucidPlan does.*
